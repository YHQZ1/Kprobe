## CRITICAL — Fix before any real data touches this system (6 issues)

**CRIT-01 — Vector double-writes every raw event to ClickHouse: table contains every event twice**
Files: `infrastructure/vector/vector.toml`, `engine/store/clickhouse.go`

The `[sinks.clickhouse]` block in Vector writes every parsed raw event directly to `kprobe.kernel_events`. The engine also writes the enriched, syscall-paired version of the same event to the same table after processing. The result is that every event exists twice: once with `duration_ns=0`, `trace_id=""`, `transaction_id=""` (the raw Vector write), and once with real latency and correlation data (the engine write). There is no flag, column, or deduplication key that distinguishes them. Every query — timeline renders, replay loads, `QueryEvents`, `QueryTimeRange` — silently mixes the two rows. `SUM(duration_ns)` is wrong. Gantt bars render as double. Replay loads double the events in sequence order. The entire data store is structurally corrupt from day one.

Fix: Delete the `[sinks.clickhouse]` block from `vector.toml` entirely. Vector's sole job is to parse JSON off `kernel.raw` and publish to `kernel.enriched`. The engine must be the sole writer to `kprobe.kernel_events`. If a raw event audit trail is needed, write it to a separate `kernel_events_raw` table with its own TTL.

**CRIT-02 — Single-row ClickHouse inserts will trigger "Too many parts" and crash the database at kernel event rates**
File: `engine/store/clickhouse.go → InsertEvent`

Every kernel event calls `conn.Exec(ctx, "INSERT INTO kprobe.kernel_events ...")` individually. ClickHouse is an OLAP engine that stores each insert as an immutable on-disk part and merges them in background threads. The default part limit per partition is 300 active parts. At eBPF event rates — easily 5,000–50,000 events per second on a busy financial host — this limit is hit within seconds of startup. ClickHouse then throws `DB::Exception: Too many parts in all partitions in total`, throttles all inserts, and the node becomes unresponsive. This is not a load problem; it is a guaranteed crash at any realistic throughput.

Fix: Replace `InsertEvent` with a batched writer. Accumulate events in a `[]types.KernelEvent` slice protected by a `sync.Mutex`. Run a background goroutine that flushes via `conn.PrepareBatch` on a 1-second timer OR a 5,000-event size threshold, whichever fires first. This is the required, documented ingestion pattern for ClickHouse and reduces part creation by 3–4 orders of magnitude.

**CRIT-05 — Unchecked Neo4j type assertions will panic and crash the gRPC server process**
File: `api/handlers/causal.go → QueryCausalChain`

Every property access from Neo4j uses a bare, unchecked type assertion: `node.Props["timestamp_ns"].(int64)`, `rel.Props["cause_type"].(string)`, `node.Props["service_name"].(string)`, etc. The Neo4j Bolt driver's behaviour for numeric types is protocol-version and value-dependent — it can return `int64` or `float64` for the same property across different driver or server versions. Any missing property (from a partial write during a previous engine crash, a hand-inserted test node, or a future schema addition) causes a nil map lookup that returns the zero value of `any`, and then the type assertion panics. This panic is unrecovered, propagates up through the gRPC handler, and crashes the entire server process. All connected clients — stream subscribers, active replay sessions, timeline queries — lose service simultaneously until the process restarts.

Fix: Replace every bare assertion with a two-value form: `val, ok := node.Props["timestamp_ns"].(int64); if !ok { val = 0; log.Printf(...) }`. Write a small helper set — `propString`, `propInt64`, `propUint64` — each of which returns a typed fallback and logs a warning on mismatch. These helpers should never panic.

**CRIT-06 — Hardcoded credentials in two independent config paths for the same database — will silently diverge in production**
File: `api/main.go`

The API opens ClickHouse twice. The first connection uses the native `clickhouse.Options{}` struct, reading from `CLICKHOUSE_ADDR`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASS`. All credentials come from one config struct. Change all default password values to `""` — forcing explicit configuration rather than insecure defaults.

**HIGH-01 — O(n²) causal inference cross-join will max a CPU core at realistic event rates**
File: `engine/inference/engine.go → processWindow`

The causal inference is a brute-force cross-join: `for i ... for j := i+1 ...`. At 5,000 events per 100ms window — conservative for a financial host with multiple services — this produces 12.5 million `inferCause` calls per tick. Each call involves PID/TID comparisons and a type-pair switch. The single goroutine running `processWindow` maxes out, the ticker falls behind, the Kafka consumer lag grows unboundedly, and the engine effectively freezes. This is not a future scaling problem; it will manifest on any reasonably loaded host.

Fix: Before comparing, partition `events` into `map[uint32][]KernelEvent` keyed by `TID` for same-thread pairs and by `PID` for same-process. Only execute `inferCause` within each partition. Maintain a small separate rolling window (last 200 events) of `sched_switch` and `page_fault` events for cross-process edge detection. This reduces complexity from O(n²) to O(k²) per partition where k is typically 2–10.

**HIGH-02 — Kafka at-most-once delivery: engine events are permanently lost on crash**
File: `engine/consumer/kafka.go → Consume`

`kafka-go`'s `ReadMessage` commits the offset to the broker before the handler callback runs. If the engine process crashes between receiving a message and completing both the ClickHouse insert and the Neo4j write, the events are permanently lost — the broker considers them consumed. For a tool whose primary value proposition is deterministic incident replay from a complete event log, data loss in the ingestion path is a correctness violation. Gaps in the event sequence mean replay sessions will reconstruct the wrong causal timeline.

Fix: Switch to `FetchMessage` (no auto-commit) followed by manual `CommitMessages` after the handler completes. For true at-least-once semantics, ensure the downstream writers are idempotent: use `ReplacingMergeTree` in ClickHouse or add a dedup key, and rely on Neo4j's existing `MERGE` (already idempotent). The cost is one extra Kafka round-trip per batch; use batch commit to amortise it.

**HIGH-03 — `inferCause` emits `"SEQUENTIAL"` for both semantically matched pairs and completely unrelated events**
File: `engine/inference/engine.go → eventPairToCause`

The last two cases of `eventPairToCause` are identical: `case from == to: return "SEQUENTIAL"` and `default: return "SEQUENTIAL"`. A `tcp_send` followed 40ms later by a `page_fault` on the same PID — with zero semantic connection — produces the same `CAUSED` relationship in Neo4j as a genuinely sequential operation. At scale, this floods the causal graph with thousands of meaningless edges per second. `QueryCausalChain` returns dense, noisy graphs for every transaction, making the entire causal analysis feature unreliable. Users cannot distinguish real causal paths from coincidental temporal proximity.

Fix: The `default` case must `return ""` (no edge created). Separately, re-examine `from == to`: same-type consecutive events are temporally ordered but not necessarily causally related. Consider returning `""` there too unless same-type pairs on the same TID are genuinely sequential (e.g. two consecutive `sys_read` calls where the second depends on the first).

**HIGH-04 — ClickHouse JSON payload built with `fmt.Sprintf` — malformed if BlockOp contains special characters**
File: `engine/store/clickhouse.go → InsertEvent`

The `payload` column value is assembled via `fmt.Sprintf` with direct string interpolation of `event.Payload.BlockOp` (a `*string`) using the `%s` format verb. The value is not escaped. If `BlockOp` contains a double-quote character — which is possible from block device operation strings on some kernels — the resulting JSON is structurally invalid. ClickHouse's `?` parameter binding protects against SQL injection but the JSON string is already assembled before it reaches the driver. ClickHouse stores it as a broken JSON object. Downstream analytical queries using `JSON_VALUE` or `JSONExtract` on the payload column will silently return null for all rows with this field.

Fix: Define a `payloadJSON` struct mirroring the payload fields. Populate it from the event, marshal with `json.Marshal`, and pass the resulting `[]byte` as the parameter value. This guarantees valid, properly escaped JSON regardless of field content.

**HIGH-05 — `EventType.Valid()` is never called after Kafka deserialization — junk event types flow into both databases**
File: `engine/consumer/kafka.go → Consume`

After `json.Unmarshal`, the `event_type` field is accepted as any arbitrary string. The `Valid()` method on `EventType` is defined and correct but never invoked. A misconfigured producer, a schema version mismatch, a corrupted Kafka message, or a future event type added to the probe without updating the engine will silently insert unknown event types into ClickHouse and Neo4j. **MED-01 — `pairSyscall` and `pairBlock` key collides across PID namespaces — events from different containers pair with each other**
File: `engine/enrich/enricher.go`

The pairing key is `(PID << 32) | TID`. Linux PID namespaces reset PIDs to small values starting from 1. In a containerised environment — which is the primary deployment target for this tool — two containers can trivially have identical `(PID, TID)` pairs (e.g. both have PID 1, TID 1 for their init process). An `sys_enter_read` from container A will incorrectly pair with an `sys_exit_read` from container B, producing a fabricated `duration_ns` and wrong `return_value` attributed to the wrong container's process. The pairing maps will also retain stale in-flight entries from dead containers, causing unbounded memory growth.

Fix: Add `CgroupID uint64` to the `KernelEvent` struct. In the eBPF probe, populate it with `bpf_get_current_cgroup_id()`. Build the pairing key as `fmt.Sprintf("%d:%d:%d", event.CgroupID, event.PID, event.TID)` (or pack all three into a struct key). Add a TTL-based eviction for entries in `syscallInFlight` and `blockInFlight` that exceed a maximum age (e.g. 5 seconds) to prevent memory leaks from unmatched events.

**MED-07 — `inferCause` treats same-TID and same-PID causality identically — cross-thread edges are overstated**
File: `engine/inference/engine.go → inferCause`

```go
if a.TID == b.TID { return eventPairToCause(a.EventType, b.EventType) }
if a.PID == b.PID { return eventPairToCause(a.EventType, b.EventType) }
```

Both branches call the same function with identical logic. Same-thread (TID match) events are definitively causally ordered — the thread executes sequentially. Same-process/different-thread events share memory but have concurrent execution; a causal link requires synchronisation evidence that this code does not check. Treating them identically produces cross-thread causal edges with no evidence of synchronisation. A `sys_write` on thread A and a `sys_read` on thread B in the same process at similar times will get a `READ_TO_WRITE` edge even if they are completely unrelated operations on different file descriptors.

Fix: Differentiate the branches. For same-TID, use `eventPairToCause` as-is. For same-PID/different-TID, only emit an edge if there is additional evidence: identical file descriptor values (from `SyscallFD`), a preceding `sched_switch` that connects the threads, or an explicit socket connection. At minimum, use a different cause type string (e.g. `CROSS_THREAD_SEQUENTIAL`) so users can filter them.

**MED-08 — Ring buffer sizes are fixed at 256KB per event type — overflows silently drop events at burst load**
File: `probe/probe-ebpf/src/main.rs`

Each ring buffer is initialized with `RingBuf::with_byte_size(256 * 1024, 0)`. The userspace drain loop in `main.rs` polls all five buffers every 10ms. At a `sched_switch` rate of 10,000 events per second (normal on a loaded host), the `EVENTS_SCHED` ring buffer can hold approximately 10,000 × 24 bytes (SchedEvent size) = 240KB worth of events. This means the ring buffer can overflow within a single polling interval at moderate load. When a ring buffer overflows, the eBPF program's `reserve` call returns `None`, the event is silently dropped at kernel level, and there is no counter or metric indicating that drops occurred. The probe emits `info!` logs for successful events but nothing for dropped ones.

Fix: Increase ring buffer sizes to at least 4MB per type (`4 * 1024 * 1024`). Add a BPF map counter (`BpfHashMap<u32, u64>`) that the eBPF program increments on every `reserve` failure. Read this counter from userspace periodically and log/emit a metric when it is non-zero. Also fix the polling loop (see LOW-02).

**MED-09 — Syscall tracepoint context offsets are hardcoded — will read wrong fields on non-x86_64 or different kernel versions**
File: `probe/probe-ebpf/src/syscall.rs`

The syscall enter/exit tracepoint fields are read at hardcoded byte offsets: `ctx.read_at(16)` for `fd`, `ctx.read_at(32)` for `bytes`, `ctx.read_at(48)` for return value. These offsets correspond to the `sys_enter_read` and `sys_exit_read` tracepoint format on x86_64 with a specific kernel version. The `sched_switch` tracepoint similarly uses `ctx.read_at(24)`, `ctx.read_at(32)`, `ctx.read_at(56)` without any verification. On ARM64, on a different kernel version, or if kernel BTF (BPF Type Format) changes these struct layouts, these offsets will read garbage values silently — wrong FDs, wrong byte counts, wrong PIDs.

Fix: Use Aya's BTF-based CO-RE (Compile Once, Run Everywhere) support. Replace raw `ctx.read_at(offset)` with `ctx.read_at::<Type>(0)` on typed BTF structs, or use the `aya-ebpf`'s `bpf_probe_read_kernel` helpers with BTF field access. This makes the probe kernel-version agnostic and self-correcting on layout changes.

**MED-11 — Enricher span list grows unboundedly between `AddSpan` calls — O(n) linear scan per event**

**MED-12 — `engine/go.mod` and `api/go.mod` both on Go 1.22 but `go.work` specifies `go 1.24.1` — toolchain mismatch**
Files: `go.work`, `api/go.mod`, `engine/go.mod`

The workspace file declares `go 1.24.1`. The individual module files declare `go 1.22`. Go 1.24 introduced changes to the language spec, toolchain version semantics, and standard library behaviour. Building individual modules outside the workspace context (e.g. in CI with `go build ./...` from the module directory) will use the module's declared minimum Go version, which may produce different behaviour from workspace builds. This is a subtle CI/prod parity risk.

Fix: Align all `go.mod` files to `go 1.24.1` (or whichever version you standardise on). Add a `toolchain go1.24.1` directive to each `go.mod` to make the requirement explicit.

**LOW-01 — Frontend event type strings use kernel function names; backend uses semantic names — manual mapping will drift**
Files: `console/src/types/events.ts`, `shared/types/event.go`

Frontend: `"tcp_sendmsg"`, `"tcp_recvmsg"`, `"mm_page_fault"`. Backend: `"tcp_send"`, `"tcp_recv"`, `"page_fault"`. The `TYPE_LABELS` mapping in `mockData.ts` bridges them manually. When the backend adds a new event type or renames one, the frontend mapping must be updated by hand. There is no compile-time guarantee that they stay in sync.

Fix: Define canonical event type strings once in `kprobe.proto` as an enum. Use `protoc-gen-ts` or `buf` to generate TypeScript types from the proto. Delete `TYPE_LABELS` and the manual mapping.

**LOW-02 — eBPF publisher busy-polls all five ring buffers every 10ms regardless of load**
File: `probe/probe/src/main.rs`

The drain loop unconditionally sleeps 10ms between polls. Under low load this adds up to 10ms of event delivery latency. Under high load, events accumulate in ring buffers between polls and arrive in bursts. Aya's `AsyncRingBuf` provides file-descriptor-backed readiness — the ring buffer signals the tokio runtime when data is available, enabling true zero-latency wakeup.

Fix: Replace the polling loop with `tokio::select!` on `AsyncRingBuf` readiness for each of the five maps. This gives event-driven delivery, eliminates the sleep latency, and reduces CPU usage at idle.

**LOW-03 — `replay/injector/injector.go` applies `ExtraLatencyNs` by adding to `DurationNs` but this does not actually delay playback**
File: `replay/injector/injector.go → applyExtraLatency`, `replay/session/session.go → runPlayback`

`applyExtraLatency` adds `cfg.ExtraLatencyNs` to `event.DurationNs`. But `runPlayback` uses `TimestampNs` differences between consecutive events to compute inter-event delays — it never reads `DurationNs` for timing. Adding to `DurationNs` changes the value stored in the event struct and displayed in the UI, but does not add any real delay to the playback timing. A user who sets "extra latency 200ms" will see 200ms added to the displayed duration field, but the playback will run at the same real speed.

Fix: Either use `DurationNs` as the delay source in `runPlayback` (replacing the timestamp-difference approach), or apply `ExtraLatencyNs` directly to the timestamp delta in `runPlayback` instead of to `DurationNs`. The current `applyTimeout` which overwrites `DurationNs` with `TimeoutOverride` has the same problem.

**LOW-04 — `replay/session/session.go → Stop()` resets cursor to 0 instead of to the last position**
File: `replay/session/session.go → Stop`

`Stop()` sets `s.state = StateReady` and `s.cursor = 0`. This means Stop is equivalent to a full reset. A user who stops a replay mid-way through and then starts it again begins from the first event, not from where they stopped. The intended behaviour for Stop in a media-player model is to halt playback and retain position; reset is a separate explicit action.

Fix: Remove `s.cursor = 0` from `Stop()`. Add a separate `Reset()` method that sets cursor to 0. Expose `Reset` in the gRPC `Control` RPC as a new command alongside `play`, `pause`, `stop`, `seek`.

**LOW-05 — `inferCause` has no evidence check for `sched_switch → blocking` cross-process edges**
File: `engine/inference/engine.go → inferCause`

```go
if a.EventType == types.EventTypeSchedSwitch && isBlocking(b.EventType) {
    return "SCHED_DELAY"
}
```

This fires for any `sched_switch` within the 50ms window of any blocking syscall, regardless of whether the sched event was on the same CPU, involved the same PIDs, or was actually the cause of the blocking delay. A `sched_switch` on CPU 3 preempting PID 9000 will create `SCHED_DELAY` edges to every `sys_read` on any CPU within 50ms. On a loaded host this generates thousands of false positive sched-delay edges per second.

Fix: The `sched_switch` event contains `SchedPrevPID` and `SchedNextPID`. Only create a `SCHED_DELAY` edge if `sched_switch.SchedNextPID == b.PID` (the scheduled-in process is the one that ran the blocking syscall) AND `sched_switch.CPU == b.CPU`.

**LOW-06 — `console/src/pages/Settings.tsx` stores settings in `localStorage` with no schema version — silent breakage on settings changes**
File: `console/src/pages/Settings.tsx`

Settings are serialized to `localStorage` as raw JSON via `JSON.stringify(settings)` and merged with `{ ...DEFAULTS, ...JSON.parse(raw) }` on load. If a future version of the app renames a settings key, removes a key, or changes a value's type, the old stored JSON will be merged with `DEFAULTS` producing unexpected states. For example, if `probeOverhead` is renamed to `probeMode`, the old `probeOverhead` key survives in localStorage, the new `probeMode` gets the default value, and nobody notices.

Fix: Add a `version: number` field to the `Settings` type. In `loadFromStorage`, check the version. If it does not match the current version constant, discard the stored settings and return `DEFAULTS`. This prevents stale settings from silently corrupting the UI state after upgrades.

**LOW-07 — The `Makefile` `test-go` target runs tests in the `shared` module but `shared` has no test files**
File: `Makefile`

`test-go` runs `cd shared && go test ./...`. The `shared/` module contains only `types/event.go` and `domain/types.go` with no `_test.go` files. This will pass vacuously but gives false confidence. More critically, the causal engine's inference logic — `inferCause`, `pairSyscall`, `pairBlock`, `enrichTrace` — has no tests at all. For a system designed to diagnose financial incidents, the correctness of causal inference is the most critical property to test.

Fix: Write unit tests for `inferCause` covering all event type pairs, the timestamp ordering edge cases, and the threshold boundary. Write tests for `pairSyscall`/`pairBlock` covering the enter/exit pairing, the out-of-order case, and the key collision scenario. Write tests for `enrichTrace` covering PID match, time window boundary, and no-match passthrough.

**LOW-08 — Aya dependencies are pinned to git HEAD — builds are not reproducible**
File: `probe/Cargo.toml`

```toml
aya = { git = "https://github.com/aya-rs/aya", default-features = false }
aya-ebpf = { git = "https://github.com/aya-rs/aya", default-features = false }
```

All Aya crates are pulled from `git = "https://github.com/aya-rs/aya"` without a `rev` or `tag` pin. `cargo.lock` fixes the resolved commit at build time, but any CI pipeline that regenerates the lockfile, or any developer who runs `cargo update`, will silently pull a different Aya version. Aya is under active development with frequent breaking changes to the API and eBPF verifier compatibility.

Fix: Pin to a specific release tag or commit hash: `aya = { git = "https://github.com/aya-rs/aya", tag = "v0.x.y", ... }` or use `rev = "abc1234"`. Better: wait for Aya's crates.io releases and use version-pinned crates.

**LOW-09 — `docker-compose.yml` exposes ClickHouse native port 9000 and Neo4j Bolt port 7687 to `localhost` with no network isolation**
File: `infrastructure/docker/docker-compose.yml`

Both `9000:9000` (ClickHouse native protocol) and `7687:7687` (Neo4j Bolt) are bound to all interfaces on the host. Anyone with access to the host machine — or any process running on it — can connect directly to ClickHouse and Neo4j using the hardcoded default credentials (`kprobe`/`kprobe` and `neo4j`/`kprobe_secret`). For development this is acceptable; for any other environment it is not. Fix: For non-development environments, bind to `127.0.0.1` only: `"127.0.0.1:9000:9000"`. Add proper `depends_on` with `condition: service_healthy` for all Go services when added to the compose file. Change all default passwords to randomly-generated values provided via a `.env` file that is gitignored.

**GAP-03 — There is no graceful degradation path if Kafka is unavailable — the probe blocks or crashes**
File: `probe/probe/src/publisher.rs`

The Kafka `FutureProducer` is created at startup and used for every event. If Kafka is unavailable (network partition, broker restart, topic misconfiguration), `producer.send(record, Duration::from_secs(0))` returns an error logged as `warn!` and the event is dropped. But there is no circuit breaker, no local buffer, no backpressure to the ring buffer drain. Under a prolonged Kafka outage, the eBPF ring buffer fills, the kernel-side `reserve` calls begin returning `None`, and kernel events are silently dropped at the eBPF level. The probe continues running but is recording nothing. On a financial host, this means an outage that coincides with a Kafka hiccup produces a gap in the event log precisely when you need it most.

Fix: Add a bounded in-memory ring buffer (e.g. `VecDeque<String>`, max 100,000 events) in the publisher. On Kafka send failure, push to the local buffer. On successful send, drain the local buffer first. Log a warning when the local buffer starts filling and an error when it overflows. This gives the probe a resilience window for short Kafka interruptions.
